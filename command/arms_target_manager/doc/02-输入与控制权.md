# 输入与控制权

## 两条规则

整个模块只依赖两条规则：

1. **一个目标同时只有一个输入在写。**
2. **写的人要说明自己是谁、优先级多少、还打算写多久。**

第二条里的“还打算写多久”就是控制权的有效期。输入只要持续提交就持续续期；
停止提交，时间到了自动交还，不需要额外通知谁。

## 谁在什么优先级

| 输入 | 来源标记 | 优先级 | 一次占用 |
|---|---|---|---|
| RViz 拖动 marker | `SourceId::Rviz` | 高 | 500 毫秒 |
| VR（普通 / 全身） | `SourceId::Vr` | 普通 | 300 毫秒 |
| 程序调用旧接口 | `SourceId::External` | 普通 | 500 毫秒 |
| 摇杆 / 键盘速度 | `SourceId::ControlInput` | 不占位姿 | 不适用 |

规则：

- 高优先级可以打断普通优先级；
- 普通优先级打断高优先级会被拒绝，原因 `manual_override`；
- 同优先级不互相打断，先来的继续写，后来的收到 `busy`；
- 控制权到期后谁先提交谁拿到。

## 摇杆/键盘为什么单独处理

摇杆发的是速度，不是“目标应该在哪”。控制器会自己把速度积分成位置。

如果速度流和 VR 的绝对目标同时存在，VR 每 30 毫秒把目标设到某点，
速度在中间又把目标推走一点，表现出来就是轻微抖动或“推摇杆没反应”。

现在：

- 没人用绝对目标控制这条手臂时，速度照常发；
- VR 或拖动正在控制时，整条速度流丢弃，并打一条调试日志；
- 手部（夹爪）命令不受影响，照常转发；
- `ControlInputHandler` 不再自己积分一份 marker 可视化，避免和真实目标不一致。

## VR 与拖动同时在线

### 拖动期间

1. 每个拖动事件提交一次目标，优先级高、占 500 毫秒。
2. VR 继续按自己的节奏提交，但被拒绝，原因 `manual_override`。
3. VR 收到拒绝后在这一侧暂停，不再硬发，等控制权释放。
4. marker 停在用户拖到的位置，不会被控制器回传值拉走。

### 松手以后

1. 500 毫秒没有新拖动，控制权到期。
2. VR 下一次提交被接受。
3. 输出层用 400 毫秒从拖动终点过渡到 VR 目标。
4. 普通模式（相对映射）会先重建基准，把当前手柄位置对应当前机器人位置，
   所以恢复时不会跳到手柄的绝对位置。

### 回显

控制器会把实际接受的目标发回来。输出层收到后：

- 手动拖动之后 1 秒内只记录、不刷新显示，避免把用户刚放的 marker 拉回去；
- 其余时间正常刷新，所以 VR 控制时 marker 显示的是控制器实际目标，
  能看出限幅、插值造成的偏差。

注意这是两个不同的时间：**控制权 500 毫秒**决定“谁在发”，
**回显抑制 1 秒**决定“看到什么”。

## 单次发送模式

- **连续**：拖动实时发目标。
- **单次**：拖动只更新预览，点菜单“发送目标”才发一次；
  发的是你拖到的位置，不是 VR 的目标。

## 被拒绝时会怎样

提交返回“是否接受 + 原因”：

| 原因 | 含义 |
|---|---|
| `manual_override` | 有人在手动拖动，优先级更高 |
| `lower_priority` | 对方优先级更高 |
| `busy` | 同优先级，已经有人在写 |
| `blocked` | 这个来源被显式屏蔽（例如全身跟踪时屏蔽速度流） |
| `no_tf` | 两个坐标系之间暂时没有变换 |
| `invalid_pose` | 目标里有非法数值 |
| `no_publisher` | 这个目标没有发布器（单臂模式下的右臂） |
| `preview` | 只记录未发送（单次模式的拖动） |

## 状态怎么看

`TargetRouter` 默认不打印通道状态日志（避免拖动时刷屏）。
需要时在代码里调 `router()->status()` 拿到 `TeleopStatus`：每通道包含
`owner`（谁在写）、`active`（租约是否还有效）、`last_reason`（最近一次提交结果）、
`accepted` / `rejected`（累计计数）。

排查“为什么不动”时，也可以直接看 RViz 里 marker 是否可拖、
以及日志里的 `拖动未生效：<原因>` 限频提示。
